MLflow: keep training runs in a local experiment log

By AiCoN | Published 28 October 2026 | Sources checked 28 October 2026

When you train several model versions, a score in a terminal is easy to lose. MLflow records runs with parameters and metrics so you can find and compare them later. We tested its local Python logging and search APIs with two decision-tree runs and a SQLite database. We did not complete a working UI check, so this guide covers the verified code workflow only.

Quick facts

  • Purpose: record experiment runs, parameters and metrics. The official quickstart also covers models, which we did not test logging.
  • Tested: MLflow 3.17.2, scikit-learn 1.7.2, Python 3.10.12/Linux, explicit SQLite tracking URI.
  • Cost and licence: the code repository lists Apache 2.0. No account, card, payment or managed cloud service was used in our local test.
  • Privacy scope: only the bundled Iris dataset and experiment metadata were used. We did not inspect network traffic or prove offline operation. Local storage is not a privacy audit.
  • India: no India-specific availability was established. This was a local package workflow.

Why use it beside a chatbot?

A chat explanation can help choose a parameter, but it is not your experiment record. MLflow gives each training run a place to store the parameter value and resulting score. You can query those records without manually copying a table into a conversation. It does not decide whether a metric or test split is appropriate.

What we actually tested

On 28 October 2026 we split the bundled Iris data once using a fixed random seed and stratification. We trained decision trees with maximum depths 1 and 3 on the same training rows and evaluated both on the same 45 held-out rows. Each run logged max_depth, test_rows and holdout_accuracy. A search of the stored runs returned depth 3 above depth 1 when sorted by that metric.

Exact tested code

import mlflow
from sklearn.datasets import load_iris
from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier
from sklearn.metrics import accuracy_score
mlflow.set_tracking_uri('sqlite:///runs.db')
mlflow.set_experiment('iris-depth-comparison')
X, y = load_iris(return_X_y=True)
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.3, random_state=42, stratify=y)
for depth in [1, 3]:
    with mlflow.start_run(run_name=f'depth-{depth}'):
        model = DecisionTreeClassifier(max_depth=depth, random_state=42)
        model.fit(X_train, y_train)
        score = accuracy_score(y_test, model.predict(X_test))
        mlflow.log_param('max_depth', depth)
        mlflow.log_param('test_rows', len(y_test))
        mlflow.log_metric('holdout_accuracy', score)
        print(f'depth={depth} accuracy={score:.6f} test_rows={len(y_test)}')
runs = mlflow.search_runs(order_by=['metrics.holdout_accuracy DESC'])
print(runs[['params.max_depth', 'metrics.holdout_accuracy']].to_string(index=False))

Copied result lines

depth=1 accuracy=0.666667 test_rows=45
depth=3 accuracy=0.977778 test_rows=45
params.max_depth  metrics.holdout_accuracy
               3                  0.977778
               1                  0.666667

The results are about this single small split, not proof that depth 3 is generally better. No cross-validation, tuning search, statistical comparison or production model evaluation was performed. We also checked that the local SQLite file contained the recorded parameter and metric rows.

Run the verified Python route

Use an isolated Python 3.10 environment. The tested MLflow release requires Python 3.10 or later. Install these versions, save the code as demo.py, and run it from an empty working folder:

pip install "mlflow==3.17.2" "scikit-learn==1.7.2"
python demo.py

The relative URI sqlite:///runs.db creates or uses runs.db in the current folder. Keep that file if you want the experiment record. Rerunning the script adds two more runs to the same experiment; it does not replace the old ones. Review what you log before pointing tracking at a shared or remote server.

What remains unverified

  • The local web server served page assets, but browser UI testing stalled. We are not publishing a working-dashboard screenshot or claiming UI success.
  • No model artifacts, registry, deployment, remote server, LLM tracing, team access or managed service was tested.
  • Only two runs and one dataset split. The scores are not a benchmark of MLflow, which recorded values computed by scikit-learn.
  • We did not test telemetry controls, offline operation, security configuration or retention policies. Avoid logging secrets or private datasets without reviewing the setup.
